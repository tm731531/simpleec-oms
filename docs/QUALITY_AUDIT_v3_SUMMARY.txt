核心改進點：
================================================================================

🔴 缺陷 #1: 隱式依賴關係 → 改為顯式編碼
   - 所有 Task JSON 現在包含 blockedBy 和 blocks 字段
   - Task 系統可以自動強制依賴順序

🔴 缺陷 #2: Prompt 缺少停止條件 → 添加明確的「❌ 不要做的事」清單
   - 每個 Prompt 都明確說「完成後停止」
   - 防止 Agent 無限期繼續工作

🟢 缺陷 #3: Session 生命週期缺失 → 新增 Heartbeat + 孤立檢測
   - Team-Lead 每 30 秒檢查一次
   - 自動檢測並清理孤立 Agent

🔴 缺陷 #4: Timeout 實現不明確 → 明確的 30 分鐘檢查邏輯
   - Team-Lead 每 30 分鐘檢查一次
   - 超時時自動解鎖依賴的 Tasks

🔴 缺陷 #5: Agent 協調隱式 → 標準化的消息格式和流程
   - 明確禁止 Agent 之間的直接通訊
   - 所有通訊通過 Team-Lead 和 SendMessage

🔴 缺陷 #6: 交付物格式粗略 → 詳細的 JSON Schema 定義
   - 每個 Task 的交付物都有精確的字段定義
   - 包含「ready_for_next_phase」通行字段

關鍵設計決策（為什麼這樣改）：
================================================================================

決策 1: 保留 Sequential Phase 架構
  原因: 這是對的設計，沒必要改
  結果: 核心架構清晰，改進集中在實現細節

決策 2: 編碼所有隱式依賴
  原因: 隱式依賴是第 3 次失敗的根本原因
  實施: Task.blockedBy 和 Task.blocks
  效果: Task 系統自動強制順序，不依賴人工判斷

決策 3: 添加 Prompt 禁止清單
  原因: Agent 不知何時停止導致內存增長
  實施: 每個 Prompt 都有「❌ 不要做的事」清單
  效果: Agent 完成後停止，不自作聰明

決策 4: 實現 Session 生命週期監視
  原因: 第 4 次失敗是 parent session 死亡
  實施: Team-Lead 每 30 秒檢查，30 分鐘檢查 Session 狀態
  效果: 孤立 Agent 能被立即檢測和清理

決策 5: 明確 Timeout 檢查邏輯
  原因: v2 說了 timeout 但沒說怎麼實現
  實施: Team-Lead Prompt 中的「Timeout Check」章節
  效果: 無限期等待變成 2 小時自動解鎖

已知限制：
================================================================================

改進版 v3 解決了 4 個 CRITICAL 問題，但仍有一些已知限制：

1. Agent 能力上限
   - Opus 的處理能力有上限（文件太多可能超時）
   - 解決: 如果文件 > 10MB，預先精簡

2. 交付物格式驗證
   - 系統不自動驗證 JSON 格式
   - 解決: Team-Lead 手動檢查，或添加自動驗證邏輯

3. 動態 Timeout 調整
   - Timeout 固定為 2 小時
   - 解決: 如果實踐中需要不同時間，修改 Task 定義

4. 並行度限制
   - 因為 Task #2 和 #3 依賴 Task #1，無法完全並行
   - 解決: 這是架構的選擇，不是 bug
